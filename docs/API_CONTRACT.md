# API Contract

Behaviour and rules of the Cognify API. The Pydantic models (exposed through FastAPI's OpenAPI at `/docs`) are the source of truth for exact field types. The JSON examples below are illustrative first drafts of those models. All examples use the Maria ball-problem demo.

Design in brief: the student talks to one tutor interface. Behind it, a **reasoning step** (LLM) splits the answer into steps and diagnoses it without knowing the teaching method; code then applies the rules, checks repair and calls the rule-based `choose_strategy`; a **teaching step** (LLM) writes a reply for that diagnosis and method, or a follow-up problem. A **verification LLM** checks every reply or follow-up before the student sees it, and judges the student's follow-up attempt. **Code** owns the flow, the method choice, history and the final VERIFIED decision.

## Part A: Frontend <-> Backend

### Rules

- Every ID is a UUID v4 string (session, student, concept), generated by the backend.
- The two seeded demo learners have fixed UUIDs, defined once in the seed and in the demo config: Maria `16e82ef2-adee-4671-8393-c6b50ac91672`, Nikos `00915798-79f9-4362-84d0-839a0b3df9f2`.
- `display_name` is for the UI only.
- The backend owns all state, prompts, validation and writes.
- The frontend never calls a model provider.
- The hidden solution, hidden rubric and verifier notes never leave the backend.
- A bad model reply becomes a safe fallback, never a 500.
- All routes are under `/api`.
- Tutor text is not streamed (replies are checked before sending).
- Seeded data always carries a seeded flag (`is_seeded`).
- Confidence is a label (`low`, `medium`, `high`), never a percentage.
- Errors use the one error shape at the end of Part A.

### Endpoints

| Endpoint | Purpose | Caller | Input | Output | Writes | Features |
|---|---|---|---|---|---|---|
| `GET /api/health` | Liveness check | Frontend, Docker, deploy | none | `{"status": "ok"}` | nothing | F26 |
| `POST /api/answer` | Level 1: result plus short steps | Frontend (Level 1 screen) | problem, optional subject | result, steps, `counts_as_evidence: false` | nothing; never touches the learner model | F3 |
| `POST /api/session` | Start a Master session | Frontend (after depth selector) | problem, optional subject, `student_id`, `force_experiment` (demo flag) | session id, first phase, first message | new session | F6, F12 |
| `POST /api/session/{id}/attempt` | The one student-facing turn endpoint. The backend knows from session state whether this is a first thought, a teaching reply or a follow-up attempt | Frontend (Master screen) | `StudentAttempt` | `TutorTurn` or, at the end, a turn with a `Verdict` | steps, diagnosis, method choice (and experiment flag), hints used, verdict, strategy counts, concept state | F6-F17, F30 |
| `POST /api/session/{id}/exit` | Student explicitly leaves Master | Frontend (Exit button) | none | phase `exited`, the solution, `evidence_recorded: false` | session marked exited; no evidence | F6 |
| `GET /api/learner/{student_id}` | Understanding Map view | Frontend (My Learning) | student id in path | `LearnerView` | nothing | F18, F24 |
| `GET /api/strategies/{student_id}` | How You Learn view | Frontend (My Learning) | student id in path | `StrategyView` | nothing | F19, F24 |

### Schemas

**`StudentAttempt`**: just the student's text (1 to 2000 characters). Same shape on every turn. Whitespace-only text gets a short probe and is not saved.

**`TutorTurn`**: `session_id`; `phase`; `message` (the approved reply); optional `diagnosis` (steps with role, status and a quote of the student's words; main gap, or `null` when no gap is demonstrated (every step holds) or the evidence is insufficient (then the reply is a probe); alternatives with a confidence label each; confidence label); optional `method` (name, `mode`, experiment flag, reason; `null` on a probe or when nothing needs teaching); optional `follow_up` (problem text only, never the rubric); `hints_used`; `reply_check` (approved flag and a short summary).

**`Verdict`**: `result` (`VERIFIED` or `NOT YET`); `evidence`; `independent`; `remaining_gap`; `changes` with the before and after of the concept state and of the strategy counts (`changes.strategy` is `null` when the session used no teaching method, for example a correct first thought). The verdict response also carries `session_over`: `true` after VERIFIED or after the second NOT YET (then `message` says what was learned and offers to exit), `false` after a first NOT YET. After a `false`, the student sends a normal attempt and gets a `teach` turn.

**`LearnerView`**: student, seeded flag, concepts each with state and evidence lines.

**`StrategyView`**: student, seeded flag, one row per gap and method with uses, independent successes and experiments, plus `methods`: one overall row per method (uses and independent successes summed across gap types).

**Error shape**: code, message, retryable.

### Glossary of allowed values

| Field | Values |
|---|---|
| phase | `ask_first_thought`, `teach`, `stress_test`, `verdict`, `exited` |
| gap type | `recognition`, `representation`, `concept`, `procedure`, `strategy_choice`, `self_correction`, `transfer` |
| strategy | `socratic`, `visual_decomposition`, `worked_example`, `analogy`, `counterexample`, `representation_switch`, `micro_hint` |
| decision mode | `best_known`, `experiment`, `cold_start` |
| step role | `identify_quantities`, `choose_method`, `set_up`, `substitute`, `compute`, `interpret` |
| step status | `correct`, `wrong`, `missing` |
| state | `strong`, `fragile`, `weak`, `untested` (concepts also allow `verified`) |
| confidence | `low`, `medium`, `high` |
| perturbation | `wording`, `representation`, `context`, `distractors` |
| difficulty | `easy`, `medium`, `hard` |
| session status | `active`, `verified`, `not_yet_ended`, `exited` |
| attempt kind | `first_thought`, `teaching_reply`, `follow_up_attempt` |
| gateway failure | `invalid_output`, `timeout`, `provider_error` |

### Demo mode

One backend setting makes the API return the saved Maria story. The response shapes are identical, so the frontend cannot tell (F27).

### POST /api/answer (Level 1)

Request:

```json
{
  "problem": "A ball is thrown vertically upward with an initial velocity of 20 m/s. How high does it go before it starts to fall? (Use g = 9.8 m/s^2)",
  "subject": "physics"
}
```

Response:

```json
{
  "result": "20.4 m",
  "steps": [
    "At the highest point the velocity is 0 m/s.",
    "Use v^2 = u^2 - 2gh.",
    "Substitute: 0 = 20^2 - 2(9.8)h.",
    "h = 400 / 19.6 = 20.4 m."
  ],
  "counts_as_evidence": false
}
```

### POST /api/session (start Master)

Request:

```json
{
  "problem": "A ball is thrown vertically upward with an initial velocity of 20 m/s. How high does it go before it starts to fall? (Use g = 9.8 m/s^2)",
  "subject": "physics",
  "student_id": "16e82ef2-adee-4671-8393-c6b50ac91672",
  "force_experiment": false
}
```

Response:

```json
  "session_id": "d96e9546-b0bf-43a7-acdc-42f43ae8adac",
  "phase": "ask_first_thought",
  "message": "Before I help, what would you try first? Even an incomplete idea is useful.",

}
```

### POST /api/session/{id}/attempt

Request (same shape every time):

```json
{
  "text": "I found the time to the top, about 2.04 s, but I do not know how to get the height from the time."
}
```

Response, phase `teach` (the first diagnosis, a method chosen by the tool, and one small move):

```json
{
  "session_id": "d96e9546-b0bf-43a7-acdc-42f43ae8adac",
  "phase": "teach",
  "message": "Let's draw it. Sketch the ball going up and mark the point where its speed becomes 0. What do you know at that point, and what do you want to find?",
  "diagnosis": {
    "steps": [
      { "role": "identify_quantities", "status": "correct", "quote": "initial velocity of 20 m/s" },
      { "role": "choose_method", "status": "wrong", "quote": "I do not know how to get the height from the time" }
    ],
    "main_gap": "recognition",
    "alternatives": [ { "gap": "representation", "confidence": "low" } ],
    "confidence": "medium"
  },
  "method": {
    "name": "visual_decomposition",
    "mode": "best_known",
    "experiment": false,
    "reason": "Worked 7 of 9 times for you on recognition gaps."
  },
  "hints_used": 0,
  "reply_check": { "approved": true, "summary": "No answer given. Method matches: visual_decomposition." }
}
```

Response, phase `stress_test` (support removed; only the problem text, never the rubric):

```json
{
  "session_id": "d96e9546-b0bf-43a7-acdc-42f43ae8adac",
  "phase": "stress_test",
  "message": "Now I am removing the support. New problem, same underlying idea, different surface.",
  "follow_up": {
    "problem": "A stone is launched upward at 15 m/s from a balcony. How far above the balcony does it rise before it stops? (Use g = 9.8 m/s^2)"
  },
  "hints_used": 1,
  "reply_check": { "approved": true, "summary": "Follow-up keeps the principle, changes the context, does not state the answer." }
}
```

Response, phase `verdict`:

```json
{
  "session_id": "d96e9546-b0bf-43a7-acdc-42f43ae8adac",
  "phase": "verdict",
  "session_over": true,
  "verdict": {
    "result": "VERIFIED",
    "evidence": "Chose the equation that needs no time and substituted correctly, with no hints on this problem.",
    "independent": true,
    "remaining_gap": null,
    "changes": {
      "concept": { "concept_id": "44d54897-9ec4-45b9-8da1-d4ea95697d1d", "name": "Constant-acceleration kinematics", "before": "fragile", "after": "verified" },
      "strategy": {
        "gap": "recognition",
        "method": "visual_decomposition",
        "before": { "uses": 9, "independent_successes": 7 },
        "after": { "uses": 10, "independent_successes": 8 }
      }
    }
  }
}
```

Response, phase `verdict`, first NOT YET (the next attempt gets a new `teach` turn with a re-diagnosis; a failed experiment returns to the best known method):

```json
{
  "session_id": "d96e9546-b0bf-43a7-acdc-42f43ae8adac",
  "phase": "verdict",
  "session_over": false,
  "message": "Not yet. You started by finding the time again. Let's try a different way in.",
  "verdict": {
    "result": "NOT YET",
    "evidence": "Started by finding the time instead of choosing the equation that needs no time.",
    "independent": true,
    "remaining_gap": "recognition",
    "changes": {
      "concept": { "concept_id": "44d54897-9ec4-45b9-8da1-d4ea95697d1d", "name": "Constant-acceleration kinematics", "before": "fragile", "after": "fragile" },
      "strategy": {
        "gap": "recognition",
        "method": "visual_decomposition",
        "before": { "uses": 9, "independent_successes": 7 },
        "after": { "uses": 10, "independent_successes": 7 }
      }
    }
  }
}
```

After the second NOT YET the same shape is returned with `session_over: true`, and the outcome is recorded as not verified.

## Part B: Contracts between backend pieces

For the teammate building the AI side. These never cross to the frontend.

### `choose_strategy` tool

- **In:** gap type, concept, student.
- **Out:** method, decision mode, reason, evidence counts (plus days since the last success).
- **Consumer:** `AgentTutor` calls it in code after the reasoning step (not a model tool call), for the diagnosed gap; code records the choice. No call on a probe or when there is no gap.

```json
{ "student_id": "16e82ef2-adee-4671-8393-c6b50ac91672", "gap_type": "recognition", "concept": "constant-acceleration kinematics" }
```

```json
{
  "method": "visual_decomposition",
  "mode": "best_known",
  "reason": "Worked 7 of 9 times for you on recognition gaps.",
  "evidence": { "uses": 9, "independent_successes": 7 },
  "last_success_days_ago": 6
}
```

### Tutor agent output

One teaching turn is two model calls with code in between (`app/tutor/agent.py`):

- **Reasoning step in:** problem, the student's text, the final answer. Never the method, the history or the solution route.
- **Reasoning step out (`TutorDiagnosis`):** steps with role, status and quote; dimension ratings with evidence; `main_gap` (nullable); alternatives; confidence label; `evidence` (`sufficient` or `insufficient`); optional `error` for a wrong step: `student_did`, `actually_gives`, `asked_for`, `mismatch` (what the student's result really is versus what is needed). The teaching step targets the mismatch; the reply verifier checks that the reply does.
- **Code:** the model proposes a draft; code decides. A step whose quote cannot be found in the student's text (allowing for formatting) is not observed and is dropped, never turned into a missing step. In work with no gap and no wrong step, unnarrated missing steps are dropped too. A wrong step must state its `error`. All steps missing with nothing to go on means insufficient evidence; all steps correct means no gap. `gap_repaired` is decided by code: the step where the previous gap showed (`TeachRequest.prior`) is now correct. The mode is `teach`, `probe` (insufficient evidence, no gap being taught) or `acknowledge` (no gap, or repaired: fixed message, no teaching call).
- **Teaching step in:** the finished diagnosis, the gap step, the `choose_strategy` result (or none for a probe), and the retry reason after a rejection. **Out:** the reply only. On rejection only this step reruns, so the diagnosis cannot change.
- **Out of the turn (`TutorTeachingOutput`):** the diagnosis fields plus `gap_repaired` and the approved reply; or the follow-up problem with concept invariant, target gap, target step, perturbation, difficulty and hidden rubric.
- **Consumer:** the verification LLM checks the reply first; then code builds the `TutorTurn` for the frontend.

Teaching turn:

```json
{
  "steps": [
    { "role": "identify_quantities", "status": "correct", "quote": "initial velocity of 20 m/s" },
    { "role": "choose_method", "status": "wrong", "quote": "I do not know how to get the height from the time" }
  ],
  "dimensions": [
    { "name": "recognition", "state": "weak", "evidence": "Found the time but did not see a way to get the height without it." },
    { "name": "procedure", "state": "strong", "evidence": "Time to the top computed correctly." }
  ],
  "main_gap": "recognition",
  "alternatives": [ { "gap": "representation", "confidence": "low" } ],
  "confidence": "medium",
  "gap_repaired": false,
  "reply": "Let's draw it. Sketch the ball going up and mark the point where its speed becomes 0. What do you know at that point, and what do you want to find?"
}
```

Follow-up problem:

```json
{
  "follow_up": {
    "problem": "A stone is launched upward at 15 m/s from a balcony. How far above the balcony does it rise before it stops? (Use g = 9.8 m/s^2)",
    "concept_invariant": "Constant-acceleration motion; choose the equation that needs no time.",
    "target_gap": "recognition",
    "target_step": "choose_method",
    "perturbation": "context",
    "difficulty": "medium",
    "hidden_rubric": [
      "Chooses v^2 = u^2 - 2gh without first finding the time",
      "Substitutes u = 15 and v = 0",
      "Reports about 11.5 m"
    ]
  }
}
```

### Follow-up request (session flow → tutor)

`FollowUpRequest` carries the student's own work for a personal follow-up (F14): `student_answers` (their messages before the stress test), `last_steps` (the last teaching turn's steps, where the gap showed) and `method` (the method used while teaching), besides the problem, solution, concept, gap and hints. The follow-up is also the stress test (F15): one fresh problem, no support.

### Verifier result

- **In:** a tutor reply (reply check), a follow-up problem (follow-up check), or the student's follow-up attempt with the hidden rubric (student check).
- **Out:** mode (`reply_check`, `follow_up_check`, `student_check`); approved or rejected; rejection reason (`answer_leak`, `heavy_hint`, `method_drift`, `off_target`, `shaming_tone` for replies; `invalid_followup`, `answer_leak` for follow-ups; `not_independent` for the student check); a short note; for the student check: correct, reasoning quality label, and the independence input (`own_work`).
- **Reply check in:** also the diagnosed gap, the gap step with the student's words, the error mismatch, the chosen method's definition (`app/tutor/methods.py`, the same text the teaching step gets) and the language. Method adherence is judged by what the move does, not by its words.
- **Follow-up check:** code first rejects a follow-up that is the original with new numbers (word overlap) or in the wrong language; then the verifier checks principle, target step, solvability and that it gives no hint or answer.
- **Student check:** code also sets `own_work` to false when the answer shows no reasoning (a bare result), whatever the verifier said.
- **Consumer:** code. A rejected reply is regenerated with the reason up to 2 times, then the safe fallback question is sent. A rejected follow-up is regenerated up to 2 times; if none passes, or the student check fails, the call raises and the session returns a retryable error (there is no fake follow-up and no fake judgement). The final VERIFIED decision is code's (hint count and independence come from code, not from the verifier alone).

Rejected reply:

```json
{ "mode": "reply_check", "approved": false, "reason": "answer_leak", "note": "The reply states the final height." }
```

Rejected follow-up:

```json
{ "mode": "follow_up_check", "approved": false, "reason": "invalid_followup", "note": "The problem needs a different principle, not just a different surface." }
```

Student check:

```json
{
  "mode": "student_check",
  "correct": true,
  "reasoning_quality": "strong",
  "own_work": true,
  "note": "Used the time-free equation and substituted correctly; hint count is decided by code."
}
```
